What are SSDs?
- Invented in 1980 by Fujio Masuoka at Toshiba
- Based on flash memory
	- Stores information via electrical charges in memory cells
- SSDs have no mechanical parts
	- SSDs use transistors (just like DRAM), but data written to SSD is non-volatile
		- i.e., it persists after power loss
	-  NAND-based flash is the most popular technology, so we’ll focus on it
- SSDs have higher $ cost per bit than HDDs, but better performance
-  Writing to SSDs is more complicated than writing to HDD
	- This has implications for file system design

page (read/write unit) vs block (erase unit)
tunnel injection forces electrons into the floating gate
tunnel release forces electrons out of the floating gate

every cell has a limited lifetime as we continue to use the cell. Insulator degrades over time

What is Single-Level Cell (SLC)?
- One charge threshold
- High charge = 0
- Low charge = 1
- Longer lifetime

What is Multi-Level Cell (MLC)?
Multiple charge thresholds
• Can represent multiple values
• Highest charge = 0
• High charge = 1
• Low charge = 2
• Lowest charge = 3
• Shorter lifetime

MLC typically refers to a cell that can represent 2 bits of data. TLC (triple-level cell) can represent 3 bits of data, and QLC (quadruple-level cell) can represent 4 bits of data per cell.

How to update block? (bad approach)
Consider updating a file system block (e.g., inode block)
1. Find the (flash) block containing the target page
2. Read all active pages in the block into controller memory
3. Update target page with new data in controller memory
4. Erase the block (high voltage to set all bits to 1)
5. Write entire block to drive
• Problem!
• Some FS blocks are frequently updated
• SSD pages wear out due to limited number of program/erase cycles

## Issue #1: Write unit != Erase unit
- After a write, a page must be erased before it can be re-written.
- But… Can only erase entire blocks at one time!

**<u>Defn</u>**: *write amplification* is
$$\frac{\text{write traffic from flash chips to FTL}}{\text{write traffic from client to SSD}}$$

example
To illustrate this, consider the following example: suppose a client writes 1 GB of data to an SSD, but the FTL needs to perform garbage collection, which requires copying 0.5 GB of data from one block to another. In this case, the write traffic from the client to the SSD is 1 GB, but the write traffic from the flash chips to the FTL is 1.5 GB (1 GB original write + 0.5 GB copy). The write amplification factor would be 1.5, indicating that the SSD is writing 1.5 times more data than the client is writing. This example shows how the extra copying needed to deal with block-level erases contributes to the write amplification factor.

## Issue #2 Limited Endurance
Forcing electrons across the insulating layer is destructive
- After some number of program/erase (P/E) cycles, the block “wears out”. Charge leaks.
- Endurance: expected number of P/E cycles before cell wears out
- 1 bit per cell (SLC): 50-100K P/E cycles
- 2 bits per cell (MLC): ~10-18K P/E cycles
- 3 bits per cell (TLC): <5K P/E cycles
- Solution: **Wear-leveling**
- Distribute writes equally to all blocks, to avoid fast failures of a frequently updated block.
- This is done the flash translation layer (FTL)
	- This sits between the file system and the flash chips

What is the Flash Translation Layer (FTL)?
- Goal 1: Translate reads/writes to logical blocks into reads/erases/ programs on physical pages and blocks.
	- Allows SSDs to export the simple “block interface” that hard disks have traditionally exported
- Goal 2: Reduce write amplification (i.e., the amount of extra copying needed to deal with block-level erases).
- Goal 3: Avoid early wear-out of frequently written logical blocks.
	- Logical blocks are file system blocks

FTL is typically implemented in hardware in the SSD, but is implemented
in software for some SSDs

What are some SSD Algorithms?
 - Performed by FTL in controller (flash translation layer)
- Wear leveling
	- Always write to new physical location
	- Keep a map from logical FS block number to current SSD block and page location
	- Old versions of logically overwritten pages are "stale"
	- Where does it store the map?
	- Controller memory is volatile so we have to deal with power outages
		- SSDs have capacitors installed to supply power to it
- Garbage collection
	- Reclaiming stale pages and creating empty erased blocks
- RAID 5 (with parity checking) striping across I/O channels to multiple NAND chips

FTL Approach: Log-based mapping
- Basic idea: Treat the physical blocks like a log
- Send data in each page-to-write to the end of the log
- Maintain a mapping between logical pages and the corresponding physical pages in the SSD

# FTL Mapping
- Log-based mapping – fs block to flash block+page changes on each write
- Page-based mapping
	- For each file system block, record flash block+page where it is stored
	- high memory overhead for mapping table
- Block-based mapping
	-  Group consecutive file system blocks into a chunk matching flash block size
	- Mapping table holds chunk-to-block translation
	- High write cost
	- keep a pointer per block of the device
	-  reducing the amount of mapping information by a factor of $\frac{\text{size}_\text{block}}{\text{size}_{page}}$
- Hybrid
	- FTL sends writes to small set of log blocks, per-page mappings only for these
	- Block-level mappings for all other blocks
	- Periodically convert log block into regular block and replace with new log block

# Garbage collection (GC)
 Requires extra read and write traffic
- Overprovisioning makes GC less painful
- FTL exposes a logical page space that is smaller than the physical page space
- By keeping extra, “hidden” pages around, the FTL tries to defer GC to a background task (thus removing GC from critical path of a write)
	- This is like the *paging daemon* in virtual memory
		- We can allocate a new frame immediately
	- We will never run out of page-based mapping for every regular write, never run out of log blocks to write to
- FTL will also occasionally shuffle live (i.e., non-garbage) blocks that never got overwritten
- <span style="background:#9254de">Why?</span>
	- We need to ensure Wear-Leveling
	- Suppse FTL doesn't shuffle live. If we have video files to put on SSD
	- Other half of SSD are going through updates after updates
	- Other parts of SSD will be worn out much faster than where the video files are

# File Systems and SSDs
• Typically, same FSs as for hard disk drives
	• Ext4, Btrfs, XFS. JFS and F2FS designed to support SSDs
• No need for the FS to take care of wear-leveling
	• Done internally by the SSD
	• But the TRIM operation is used to tell the SSD which blocks are no longer in use. (Otherwise, a delete operation doesn't go to disk)
• Some flash file systems (F2FS, JFFS2) help reduce write amplification
	• Especially for small updates – e.g., FS metadata
• Other typical HDD features – do we want these?
	• Defragmentation
	• Disk scheduling algorithms

• SSD is a high-performance storage device using flash memory
	• No moving parts – much faster, but currently costs more
	• Organized in pages and blocks
	• A block must be erased before its pages can be written to
• FTL (flash translation layer)
	• Makes an SSD appear like a traditional block device
	• Maps logical block numbers to physical pages
	• Manages several flash-specific challenges
		• Wear-leveling
		• Garbage collection
	• Accepts TRIM commands to improve efficiency of GC
