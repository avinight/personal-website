## Pipeline dimensions

MIPS R2000
Coprocessor 
- generates addresses
- handles control
- handles exceptions

CPU
- pipelined processor
- Autonomous multiplier/divider

Advantages of increasing pipeline depth
- increases frequency, reduces cycle time
Disadvantages of increasing pipeline depth
- Limited by pipeline registers: sequencing overhead, extra hardware
- Limited by hazards
	- More complex control and hazard detection
	- More hardware for bypassing
	- Branches resolved later in the pipeline; penalty of flush increases


Superpipelined
- when a CPU has more than the classical 5 stages, it is superpipelined

Advantages of increasing pipeline width
- increases ideal IPC beyond 1
	- allows more than one instruction in a stage at a time
	- more options to exploit instruction level parallelism
Disadvantages of increasing pipeline width
- Significant changes to our existing pipeline structure  
- Complex scheduling  
- Increased cost in Area and Power


Superscalar CPU
- m is the ideal number of instructions fetched into the pipeline
- if m=1, the processor is simply scalar
- m-way superscalar; here m=2

Limits of superscalar
- Large m needs lots of ILP
	Limits to hardware discovering ILP
	Limits to ILP
- Back-end needs at least m functional units
	Number of forwarding paths grows quadratically with number of functional units
- More ports are costly
	e.g., register file needs more read ports
- Power
	Increasing m and k makes for a very power-hungry processor
## Instruction scheduling

Static scheduling
- Instructions leave front-end in program order
- All data dependencies are resolved in the front-end
- e.g., our five-stage pipeline

Dynamic scheduling
- Instructions can leave front-end out-of-order
- The commit stage (formerly write back) ensures program order is observed

Functional units problems
- Different units for different classes of operations
	- May or may not be pipelined
- Separate register files for integer and floating-point
- Functional units have different latencies
Data hazards in an FU
- Out-of-order write hazards
- What is the cache miss latency?
Structural hazards in an FU
- in the Execute stage: Non-pipelined FUs
- in the Write back stage

**The issue stage** solution to FU problems
- Add an issue stage to the front-end of the pipeline
- The issue stage will stall until there are no dependence problems

When to issue instructions:
1. Is the FU busy?
2. Are the inputs ready? (RAW)
3. Is it correct to write back the result? (WAR, WAW)
4. Can we write back the result? (structural)

A table (in hardware) tracks the status of FUs
- Add to the table when (precondition: no hazards)
- Remove from the table when (after write-back)

Can we detect hazards?
```
1. any(x.src1 == y.fi or x.src2 == y.fi for y in table) // RAW
2. any(x.dest == y.fj or x.dest == y.fk for y in table) // WAR
3. any(x.dest == y.fi for y in table)                   // WAW
```
So that I can issue instruction x


What are the assumptions of issuing in-order?
Instructions are issued when:
- There is no RAW hazard
- The FU is available
- (this is less strict than the earlier precondition)
The operands are read by the issue stage and saved in the functional unit

What are some impacts of issuing in-order on hazards?
WAR hazards are eliminated
- Table no longer needs source columns
WAW hazards are still possible
- FUs have different latencies
