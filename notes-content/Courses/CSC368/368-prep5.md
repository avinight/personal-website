# Goals
1. List and describe speculative approaches used in the processor pipeline and memory system
2. Trace the state and accuracy of a simple branch predictor given a snippet of code

Speculation: how can hardware look at runtime patterns and exploit them

Control Problem:
- Avoid stalls with branch prediction
- Static branch prediction is inaccurate
- Can we dynamically predict branches based on control flow patterns

Memory Problem:
- Avoid long latency with cache hierarchy
- A cache miss is still very expensive
- Can we anticipate misses based on memory reference patterns?

How do we execute speculation?
1. Guess the branch target in the fetch stage
2. Verify the guess by executing the branch
	- Mispredictions must be flushed from the pipeline
- Do not store values to registers or memory until guess is verified
	- Not too bad for an in-order pipeline
	- Out-of-order pipeline?

Branch prediction DS:
- for targets:
	- Branch Target Buffer using program counter as key
- for direction:
	- dictionary

What is prefetching?

examples of hardware prefetchers:

# Quiz


Consider the following code:

```C
struct foo {  
 int x;  
 int y;  
};  
  
...  
struct foo array[N];  
...  
for(int i = 0; i < N; i++)  
    array[i].x = i + 1;
```

Assume an integer is 4 bytes (and, so, struct foo is 8 bytes in size). What is the stride between the memory accesses inside the for loop?

Give your answer in bytes (e.g., if your answer is one byte, write: 1).



Match the branch instruction with the data structure that is used to predict its target. If more than one data structure matches, select the _best_ one.
- Conditional branches: BTB
- Return instructions: RAS

Which data structure is the most accurate for predicting the direction of branches inside nested loops?
- 1-bit counter
- 2-bit saturating counter
- Branch target buffer (BTB)
- Return address stack (RAS)

What problems are likely to arise from an overly-aggressive prefetcher?
- **May evict data that needs to be used again**
- **Increases requests to the memory system**
- Increases the frequency of data hazards
