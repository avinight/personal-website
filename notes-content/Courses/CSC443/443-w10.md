## Questions

Problem with row stores:
- We only need a little of each row
- But storage access granularity is coarse
- Memory can also only be accessed in cache lines
- Reading more than we are interested in wastes bandwidth
Row stores are good for selective queries/updates
Column stores are good for batch statistical calculations and updates

Why the 30 year gap? Storage density grew, so we store far more
data now. Processing it efficiently is more critical. This drives a
need for specialization.

Should we store each column with a materialized ID?
- No, this would slow down queries by reading more data

For fixed length data, use positional alignment

In case of variable length data we can apply indirection (unrecommended)
Best to define a schema with fixed-length fields if possible prevent indirection overhead

In column-stores, each column spans
multiple pages & queries are unselective
Scanning a column in memory would require hashing overheads for each page.

How should we handle the buffer pool (BP)?
- Better to read and map at column-granularity (or multiple pages thereof

Early materialization: return each qualifying row immediately
- Potentially more random I/Os
- More CPU branch mispredictions
- Incompatible with SIMD

Late materialization: Process each column one at a time.
- requires more memory to withhold intermediate results, but entails better cache behavior & CPU efficiency

Filter on more selective columns to reduce size of intermediate results -> IO
- use countmin, cardinality estimation, histograms

How to speed up scans? Use zone maps

Handling insertions, deletes, updates:
- Best to do them overnight

# Compression
---
- We can use bit vector
	- Pro: Fast to read & compare 1 bit per entry.
	- Con: Only applicable if there are very few values.
- We can use dictionary encoding
	- Pro: applicable across larger value spaces
	- Con: slower as we need to read more bits
- We can use run-length encoding
	- Pros: compatible with dictionary encoding & can further improve compression
	- Cons: must scan column to get entry at a given offset
# Indexing on Column stores
---

- If we have two selective queries on different columns (mutex) of the table. We can answer both queries with a full scan and late materialization.
- To avoid full scans, we employ an index from key to positional ID.
- This incurs random IO on the column we want to access. So we can sort, but its costly
	- Access to B becomes skip-sequential, rather than random. but the sorting can be an issue
- We can use a column projection. Like having multiple clustered indexes on subset of columns.
- Sort A and have B sorted by A and we enable sequential access on B.

- If we don't have mutex column queries, we can project on one sorted, and regular projection.
- We can also duplicate columns and sort them in different orders.
	- More space
	- Inserts are more expensive
	- Construction can take a long time with many projections
- We tackle the last problem with database cracking in which we adaptively quicksort each column on lookup (lazy)
