# LSM Trees and Filters
---

LSM trees 
- all modifications -> in memory buffer out of place
- when it is full, flush it to storage and sort merge with data thats already in storage
- restrict the number of runs that exists in storage

- search smaller to larger levels, this allows us to find the most recent version of a given key
- if tombstone exists, then terminate and report key doesn't exist

```
number of levels L = log_T(N/P)
N = data size
T = size ratio
P = buffer size
```


In a Tiered and Leveled LSM tree:
If you set the size ratio T to be 2
- behaviours and performance properties converge

If you set the size ratio T to be very large so the first level never runs out of space (N/P)
- Tiered degenerates to an append only file
- Leveled degenerates to a sorted file

In the query path, 
- sorted runs are implemented -> Static B-tree internal nodes
	- This reduces the cost to something like 1 I/O per level
	
# Filters
---

A filter is a compact data structure represents keys in a set and allows, might return mistakes: does a given key X exist in a set?

If a key exists, then it will say yes it exists
If a key does not exist, the filter might say no.
False positive is possible: It says it exists, but it actually doesn't exist in the set
-> with probability $\epsilon$

-  a bitmap with k-hashfunctions
- Size of filter is proportional to the size of the runs that they represent
- More memory for the filters -> fewer false positives -> fewer storage accesses

How many hash functions should we use for a bloom filter?
- What happens if we use too few hash functions?
	- More false positives, not enough memory
	- One is too few, false positive occurs whenever we hit a 1 potentially
	- By adding hash functions, we decrease the false positive rate
- What happens if we use as many hash functions as the number of bits? (Too large)
	-  too many hash functions wind up increasing the FPR
- Solution: Optimal number of hash functions = $ln(2) \cdot M$
	- M is number of bits per entry in the filter
	- M is the number bits in bitmap / number of entries you want to insert

- Why one bit per entry?

Filter access cost for LSM tree
$$\text{Average negative query} = 1 + \frac{1}{2} (1 + \frac{1}{2} \cdot ( \ldots)) = 2$$
$$ \text{False Positive Rate} = 2^{-M \cdot \ln 2}$$

Worst case is when there is a false positive in each level. $\mathcal{O}(M \cdot L)$
- M hash functions
- L levels
- Extremely pessimistic

Avg Worst Case $\mathcal{O}(M + L)$
- Positive query = M ln(2)
- Avg Negative Query = 2
- L levels
