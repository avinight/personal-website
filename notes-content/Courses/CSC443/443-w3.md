# Indexing with Hash Tables and B-Trees


Zone Maps
- Split the data into ranges so it is effectively a filter. In the worst case, we still do $\mathcal{O}(\frac{N}{B})$ reads

Sorted File
- We have an IO cost of $\mathcal{O}(\log_2\frac{N}{B})$ due to binary search along each block
- We have an CPU cost of $\mathcal{O}(\log_2\frac{N}{B} + \log_2 B)$ due to binary search along each block + binary search inside a block

Binary Tree
- We have an IO cost of $\mathcal{O}(\log_2 \frac{N}{B})$ assuming the first $\mathcal{O}(\log_2 B)$ levels fit in first page
- We have a CPU cost of $\mathcal{O}(\log_2 N)$ 

Hash Table
- Read/write I/O cost: $\mathcal{O}(1)$ per random query assuming a good hash function and no key repetitions
- Downsides?
	(1) No support for range reads
	(2) Expansion leads to performance slumps
	(3) We waste 50% of capacity right after expansion

Extendible Hashing
Comparison to Hash Table
(1) Less performance slumps due to expansion
(2) Avoid wasting 50% space after expansion
(3) Directory consumes memory if it is cached, or it requires one extra I/O per operation if in storage.
(4) can’t support range queries.

B-Trees
- Search Cost = depth of tree = $\log_B \frac{N}{B} = \mathcal{O}(\log_B N)$ IO
- CPU comparisons = $\mathcal{O}(\log_B N * \log_2 B) = \mathcal{O}(\log_2 N)$ pages searched + binary search within node
- Search cost is usually bottleneck
- Read IO per insertion = $\mathcal{O}(\log_B N)$, unless stored in buffer = $\mathcal{O}(1)$
- Write IO per insertion = $\mathcal{O}(1)$
- Memory needed = $\mathcal{O}(\frac{N}{B})$ pages
- Index downsides: (1) They take up storage space (2) They must be updated as data changes
- Clustered index scan cost = $\mathcal{O}(\log_B N + \frac{S}{B})$ sequential access
- Unclustered index scan cost = $\mathcal{O}(\log_B N + S)$
- Can only sort table based on one column at a time. So usually there is only 1 clustered index per table

Why are clustered index scans $\mathcal{O}(\log_B N + \frac{S}{B})$ and unclustered index scans $\mathcal{O}(\log_B N + S)$
- In unclustered, the record is not stored within the B-tree so we cannot take advantage of sequential access
- In clustered, the record is stored within the B-tree sequentially and so we can reference S records in S/B pages 

Why is there a Garbage Collection term, do we restructure the tree if we delete?
