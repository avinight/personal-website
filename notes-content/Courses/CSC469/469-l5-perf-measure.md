# Overview
---
- Common question
	- How fast does program X run on machine Y?
- Measuring time on a computer system sounds straightforward but

- Many factors that can vary from one execution of aprogram to another
- Seemingly harmless factors can bias the measurement <= intuition

# Goals
---
- Methods to get reliable measurements of program performance
- Methods to analyze performance measurements
- Methods to identify where performance optimization matters

Two fundamental time scales
- Processor: ~1 nanosecond (10-9 secs)
- External events: ~10 milliseconds (10-2 secs)
Implications
- While waiting for external event, can execute other instructions
- Best measurement technique depends on the timescale

Measurement
- What does it mean to ask: How much time does program X take
	- CPU time
		- How many total seconds are used when executing x?
		- Measure used for most applications
		- Some dependence on other system activities
	- Actual ("Wall clock") time
		- How many seconds elapsed between start and completion of X?
		- Depends on system load, I/O times, etc.
- How does time get measured
- How does resource sharing impact measurement and performance?

Time on a computer system
- user time, system time, other time = wall clock time
- time executing instructions in the user process
- time executing instructions in kernel on behalf of user process
- everything else - idle or executing other processes, either in kernel or userspace

Process Accounting
- OS Measures runtimes using periodic timer tick
	- Eg.g HW intrerrupt generated by time device
		- Programmable Interval Timer
- Maintain 2 counts per process
	- The user time and system time
	- On each timer interrupt, increment counter for currently-executing process
		- User time, if interrupted while in user mode
		- System time, inf interrupted while in kernel mode
	- Reported by unix "time" command or getrusage in C program

Au - process A in userspace
As - process A in the kernel/system

Imprecise: timing at the granularity of the timer interval!

POSIX time
- `getrusage() `is portable, but typically has poor resolution
- `gettimeofday` (deprecated)
- `clock_gettime(clockid_t clk_id, struct timespec *tp)`
	- portable, flexible, high resolution 
	- "`clk_id`" selects what kind of time you wnat to measure
		- CLOCK_REALTIME: timestamps
		- CLOCK_MONOTONIC: elapsed times
		- CLOCK_PROCESS_CPUTIME_ID
		- CLOCK_THREAD_CPUTIME_ID
		- Additional non-portable clock ids for a given OS
- `clock_getres()` will return the resolution of a given clock

Cycle counters
- Most modern processors have built in registers that are incremented every clock cycle
	- Very fine grained
	- Maintained as part of process state
		- Possible to save & restore with context switches 
		- In Linux, counts elapsed global time
	- Special assembly code instructions to access cycle counter
	- On recent mode Intel CPUs:
		- 64 bit counter
		- RDTSC instruction sets %edx to high order 32-bits, %eax to low order 32-bits

Combining hi & lo
- C bit-wise operators are used to combine the higher-order 32 bits with the low-order 32 bits into a single 64 bit unsigned integer
1. Cast hi to 64 bit unsigned int
2. Shift left 32 bits
3. Bitwise-OR with lo

Inline Assembly
- Needed for accessing cycle counters
- Key point there is no magic
- asm() directive tells GCC "emit this assembly code here"
- You give it a template

Accessing the Cycle Counter
- Code only works on an x86 machine compiling with GCC 
- Emits `rdtsc` and two `movl` instructions
- GCC automatically adds instructions to move symbolic register value `%0` int `*hi` and `%1` into `*lo`
- GCC also adds instructions to save and restore the registers that `rdtsc` clobbers (ie. overwrites)
- Be careful with out-of order execution: see `cpuid, rdtscp` instructions
	- Force all other instructions to complete first before other transactions can start

timing with Cycle counter
- Need to convert cycles into time, which involves:
	- determine clock rate of processor
	- count number of cycles required for some fixed number of seconds
- Naive version
	- Too simple, Assumes `nanosleep()` actually sleeps for 1 sec
		- May be less (if interrupted) or more (if heavy load)

Wrap-around time
- Time before a cycle counter overflows and rests to 0
- 2 GHz machine
	- Low order 32 bits wrap around every 232 / 2 * 109 = 2.1 secs
	- High order 64 bits wrap around every 264 / (2 * 109) = 9223372037 secs
		- 293 years
- 5 GHz machine 
	- Low order 32 bits wrap every 0.86 seconds
	- Higher order 64 bits wrap every 116 years

# Hardware performance monitoring
---
Limited number of counters
Non-standard and architecture specific
Poor documentation
Extracting performance insight from low-level microarchitectural events is tough
- events are indirect signs, not direct explanations

From measurement to experiment
- Metrics - a measurable quantity that is the basis for comparison
	- Choosing a good metric requires deciding what factors are most important
	- Latency, bandwidth, throughput are common in computer systems
	- Capacity, utilization, overhead, useful work
- A system to measure
	- Model, simulation, or "live"
- A set of tests to perform on the target system
	- Benchmark
- Hypothesis/Claim to why you're running the experiment

What performance metric should be used to compare the following?
- Two disk drives
	- Read/write latency
- Two transaction processing systems
	- peak/avg, Throughput transactions/sec, mean latency, tail latency
- Two packet retransmission algorithms
	- How long it takes to recover
	- Congested?
	- Stable/transmission, how aggressive?
- Two clock scaling algorithms for reducing energy usage
	- performance drop for energy reduction
	- expected cpu lifetime

Characteristics of a good performance metric?
- Intuitive (to relevant stakeholders)
- Reliable
	- Repeatable
	- Trusted for useful comparison and prediction 
- Easy to measure
	- Measurement error is small and well understood
- Consistent
	- Definition is the same across different configurations and different systems
	- Often not true in practice (e.g. MIPS)

2. Designing Workloads

- Can't always measure "real" workload
	- Production systems are noisy, evolving, and hard to control
	- Want repeatability
	- Want to test new ideas, can't deploy in real setting
- Macro benchmarks emulate end-to-end, application-level workloads
	- May be desinged by large community
		- SPEC (CPU, memory, compiler)
		- TPC (database, transaction processing)
- Vigilance is still needed when interpreting results
	- Scaling issues

Analysis of results
- Why performance analysis is an "art" not a "science"
- Given the following measurements of throughput
	- System A: Workload 1 = 20, Workload 2 = 10
	- System B: Workload 1 = 10, Workload 1 = 20
	- What is a fair comparison?
		- perf analysis requires judgement

Some possibilities
- Absolute
- Performance of A relative to B
- Performance of B relative to A

Getting the measurement right
- Understand what you are measuring
	- What part of the system si exercised
	- Wha tis included and excluded in the measurement?
- Control sources of variation (Caching, scheduling, etc.
	- Experimental noise vs. intrinsic variablility
- Choose appropriate statistics (e.g. minimum, mean, median)
	- Know what question each statistic answers
- Use a systematic methodology
	- Avoid arbitrary choices of parameters, workloads, or configurations
	- Change one factor

Fair comparison and interpretation
- Define what "fair" means for the question begin asked
	- Same workload, constraints, or optimization effort?
- Be careful with normalization and aggregation
	- Absolution vs. relative performance
	- Averages across heterogenous workloads
- Understand what conclusions are supported
	- System A is faster for this workload vs System A is better
- Avoid overgeneralization
	- Results are conditional on workloads, inputs, and assumptions

Ethical responsibility
- Be transparent about choices and limitations
- Be cautious with persuasive framing
- Avoid presentation bias
- Remember the audience
