What is the "end-to-end argument". How should it be used in operating system design
- The end to end argument questions whether functions should be implemented by higher or lower level abstractions. It is almost always better to implement functions at higher level to reduce the risk of failures at lower level abstracitons.

Open vs Monolithic
- protection
	- Open OSes offer less protection because there is no separation of hierarchy. one module or device driver may call a more sensitive instruction.
	- Monolithic OS may provide more protection as it separates user mode and privileged mode 
- extensibility
	- Open OSes are more extensible since it is easier to add new functionality.
	- Monoliths behave like closed systems and it is harder to decouple the logic, but there are ways around it like Linux modules

# Question 3
---
- Linux kernel modules include a reference count to note how many dependencies the module is being used by. This kernel count decides whether rmmod or modprobe -r command is allowed to proceed.
	- If reference count is non-zero, the kernel blocks the unloading process to prevent the system from crashing
	- If reference count > true count, the kernel believes the module is still being used -> leading to permanent kernel memory wastage
	- If reference count < true count, this is more dangerous as we may have a use-after-free. The module is freed but the dependency jumps to a function address inside the freed module causing a kernel panic/crash
- eBPF programs are safer than modules.
	- verification of packets, optionality
	- guaranteed termination, mathematical correctness
	- sandboxing memory access
- Type 1 hypervisors sit on top of hardware, type 2 hypervisors have an underlying OS underneath.
	- Examples: Xen, Disco
	- Examples: WSL, QEMU, KVM

- Its expensive to acquire a lock on modern multiprocessors because the tradeoff is space efficiency vs latency. Regular locks are fast to acquire but cause a lot of memory bandwidth usage. Ticket and MCS locks are space efficient but take extra time to acquire the lock based on FIFO policy and pointer chasing.
- atomicity and cache coherency are expensive.

- MCS locks don't really benefit from a backoff since we don't have a thundering herd problem. However in the acquisition phase, if multiple threads enter the queue at the same time, they can contend for the tail pointer. In which case we can apply exponential backoff.
